Graphify Section 1

What Is Graphify?

Graphify is an open-source Claude Code skill (community-built, not an official Anthropic product) created by @safishamsi. It converts any codebase into a queryable knowledge graph that Claude can use to answer architecture questions with dramatically less token usage. PyPI package name: graphifyy.

How Graphify Works

Graphify uses a two-track parsing strategy depending on file type:

Track 1: Code Files

Uses Tree-sitter (a concrete syntax tree parser) to extract symbols, imports, function calls, class hierarchies, and dependency edges — entirely locally. No LLM API call. Supports: Python, JavaScript, TypeScript, Java, C++, Rust, Go, and more.

Track 2: Docs & PDFs

Routes non-code files (Markdown, PDFs, README, config files) through an LLM to extract conceptual relationships and link them into the same graph. The LLM call is optional and model-agnostic.

Output Files

  • graph.json — full structured graph (nodes, edges, metadata)
  • GRAPH_REPORT.md — human-readable architecture summary
  • graph.html — interactive D3.js graph browser

Integration into Claude Code — The PreToolUse Hook

Running graphify install writes a PreToolUse hook into ~/.claude/settings.json. This hook fires before every Claude tool call and injects relevant graph context as a system message. When you ask Claude "how does the auth flow work?", Claude already has the relevant module edges and symbol relationships in its context window — without reading dozens of files.

# Conceptual flow of the PreToolUse hook:
# User asks question
# PreToolUse fires before Claude reads any file
# graphify reads graph.json, finds relevant nodes
# Injects structured graph context as system message
# Claude answers with architectural precision
# without token-expensive sequential file reads

MCP Server Mode

Graphify also exposes itself as an MCP (Model Context Protocol) server, providing 4 tools Claude can call on demand:

  • query_graph — semantic graph search
  • get_node — fetch a specific symbol/module node
  • get_neighbors — traverse graph edges from a node
  • get_summary — high-level architecture overview

Graphify — Pros & Cons

Strengths

  • Massive token savings (49–71x): graph context replaces full file reads
  • Zero-API-key code parsing via Tree-sitter — works fully offline for code files
  • Seamless Claude integration — PreToolUse hook is invisible to the user
  • MCP mode gives Claude on-demand graph query capability
  • Language-agnostic graph representation — consistent schema across Python, JS, TS, etc.
  • Interactive HTML viewer included out of the box
  • One-command install: uv tool install graphifyy && graphify install

Weaknesses

  • Code-centric — best at code symbol graphs; doc/PDF quality depends on LLM calls
  • Static graph — doesn't auto-update when code changes; must re-run graphify
  • Community project — not an official Anthropic tool; API surface may change
  • No passage retrieval — no chunk store, no cosine search; graph only
  • No temporal awareness — graph is a snapshot, not a live view
  • Hook fires on every PreToolUse — minor latency per call
  • Token savings benchmark may not apply to text/document domains

What Graphify Is Good At

  • Understanding large, unfamiliar codebases (onboarding)
  • Architecture questions: "what calls this function?", "where is X defined?"
  • Impact analysis: "what breaks if I change this module?"
  • Reducing Claude API costs on code-heavy tasks

What Graphify Is Bad At

  • Semantic document/prose retrieval (no embeddings, no cosine search)
  • Multi-hop reasoning over factual knowledge (not designed for knowledge graphs)
  • Real-time / live queries over changing data
  • Domain knowledge that isn't captured in code structure

Graphify's Fit for GraphRAG++

Key insight: GraphRAG++'s codebase is a perfect candidate for Graphify. The backend Python modules, pipeline steps, and API endpoints form a dependency graph that Graphify can parse with Tree-sitter. This would give Claude (and developers) a structured view of the codebase without reading all files.

Two integration angles exist:

  1. Developer tooling — run Graphify on the GraphRAG++ codebase itself so Claude Code has architectural context when helping with development
  2. Feature parity — adopt Graphify's preprocessing approach (pre-build a code knowledge graph at ingest time) inside GraphRAG++'s own pipeline, when ingesting code repositories via /ingest/directory

Standard RAG Section 2

Sourced from real web research: Lewis et al. 2020 (arXiv:2005.11401), MTEB Leaderboard, RAGAS documentation (arXiv:2309.15217), Anthropic Contextual Retrieval blog, and SoTA embedding benchmarks.

The Full 8-Stage RAG Pipeline

Standard RAG (Retrieval-Augmented Generation) was introduced by Lewis et al. in 2020. The core insight: instead of fine-tuning an LLM on your data, dynamically retrieve relevant passages at inference time and inject them into the prompt.

Origin: "Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks" — Lewis et al., 2020. arXiv:2005.11401
1
Document Ingestion — Load raw sources: PDFs, HTML, code, databases. Extract text via parser (pdfplumber, BeautifulSoup, etc.).
2
Chunking — Split documents into overlapping segments. Choice of chunking strategy is the single most impactful decision in a RAG system (see below).
3
Embedding — Encode each chunk into a dense vector using a bi-encoder model (e.g., all-MiniLM-L6-v2, BGE-M3, Qwen3-Embedding).
4
Vector Index — Store embeddings in an ANN index (FAISS, Qdrant, Weaviate, pgvector). Index type determines recall vs. speed tradeoff.
5
Query Embedding — At query time, embed the user's question with the same model to get a query vector.
6
ANN Retrieval — Fetch top-k nearest chunks by cosine similarity. Optionally augment with sparse BM25 retrieval and combine via RRF (Reciprocal Rank Fusion).
7
Context Stuffing & Reranking — Optionally rerank with a cross-encoder for +33–40% accuracy. Assemble retrieved chunks into a prompt context window.
8
LLM Generation — Send [system prompt + retrieved context + query] to LLM. LLM synthesises a grounded answer.

Chunking Strategies

Chunking strategy is the highest-leverage decision in RAG. A poorly chunked corpus cannot be saved by a better retriever.

StrategyHow It WorksBest ForRisk
Fixed-size Split every N tokens with M-token overlap Baseline; simple pipelines High boundary fragmentation
Sentence-level Split on sentence boundaries (NLTK/spaCy) Well-structured prose Short chunks lose context
Semantic Embed sentences, merge until cosine drops below threshold Long documents with topic shifts Slow; variable chunk size
Parent-child (small-to-big) Index small chunks, retrieve parent for context High-precision retrieval with rich context Best recall/precision tradeoff
Late Chunking (Jina v3) Embed full doc, then chunk pooled embeddings Long-form docs needing full context embeddings Best coherence; requires Jina v3
Propositional LLM decomposes each sentence into atomic facts Knowledge-dense scientific text Expensive; 10–20x cost of fixed
Page-level One chunk = one PDF page PDFs where layout = topic Chunks often too large; irrelevant content included

Critical failure mode: Fixed-size chunking cuts across logical boundaries — a chunk ending mid-sentence about one topic and beginning mid-sentence about another causes the retriever to return irrelevant context even with a perfect embedding model.

Retrieval Strategies

MethodMechanismStrengthsWeaknesses
BM25 (sparse) TF-IDF variant with term saturation Fast; handles rare terms & exact matches No semantic understanding
Dense bi-encoder Query + doc encoded to same embedding space Semantic matching; language-agnostic Misses exact-match (keyword) queries
Hybrid + RRF Merge BM25 + dense rankings via Reciprocal Rank Fusion (k=60) Best general recall; +15–25% over either alone Slightly more complex pipeline
Cross-encoder reranking Re-score top-k with full attention over (query, doc) pair +33–40% accuracy vs. bi-encoder alone Slow — O(k) full inference calls
ColBERT (late interaction) Token-level MaxSim between query and doc embeddings High accuracy; pre-computed doc embeddings Large index footprint
BGE-M3 Single model: dense + sparse + multi-vector One model replaces BM25 + bi-encoder + ColBERT Larger model size

FAISS Index Selection Guide

Index TypeScaleRecallLatencyUse When
IndexFlatIP <100K vectors 1.00 (exact) Medium Small corpus, correctness critical
IndexHNSW <5M vectors 0.95–0.99 Sub-ms Production; best recall/speed tradeoff
IndexIVFPQ >5M vectors 0.85–0.95 Fastest Billion-scale; memory constrained

GraphRAG++ currently uses FlatIP — appropriate for 993 chunks, but will need HNSW at ~50K+ chunks.

RAG Variants (Beyond Naive RAG)

Naive RAG

Retrieve → stuff → generate. The baseline. Fails on multi-hop, ambiguous queries, and long documents. Good enough for simple Q&A over structured corpora.

Advanced RAG

Adds query transformations: HyDE (generate a hypothetical document, embed that for retrieval, arXiv:2212.10496), step-back prompting, query rewriting, query decomposition. Significantly improves recall on complex questions.

Self-RAG

The LLM decides when to retrieve and evaluates its own retrieved passages with critique tokens (ISREL, ISSUP, ISUSE). Avoids unnecessary retrieval on questions the model already knows. arXiv:2310.11511

CRAG (Corrective RAG)

Evaluates retrieved docs, triggers web search if confidence is low, uses a knowledge refinement algorithm to decompose docs into fine-grained strips. arXiv:2401.15884

RAPTOR

Recursive Abstractive Processing — embeds all chunks, hierarchically clusters them (UMAP + Gaussian Mixture), summarises each cluster, then indexes summaries alongside raw chunks. Enables retrieval at multiple abstraction levels.

RAG-Fusion

Generates N query variants with an LLM, runs parallel retrieval for each, merges results via RRF. arXiv:2402.03367. Simple and effective: +10–15% recall on ambiguous queries.

Anthropic Contextual Retrieval: Prepend a 50–100 token LLM-generated context blurb to each chunk before embedding ("This chunk is from a technical report on safety evaluations..."). Results: 35% failure reduction from contextual embeddings alone; 67% failure reduction with contextual embeddings + BM25 + cross-encoder reranking combined.

RAG Evaluation — RAGAS Framework

RAGAS (arXiv:2309.15217) is the standard evaluation framework for RAG systems. It measures four metrics without requiring human labels:

Faithfulness

Are all claims in the answer supported by the retrieved context? Measures hallucination. Score: 0–1.

Answer Relevancy

Is the generated answer relevant to the question? Penalises incomplete or off-topic answers.

Context Precision

Are retrieved chunks actually useful? Measures retrieval noise — irrelevant chunks hurt LLM generation.

Context Recall

Did retrieval find all the chunks needed to answer? Measures coverage — missing chunks cause incomplete answers.

GraphRAG++ has no evaluation framework. There is currently no way to know if a pipeline change improved or degraded answer quality. RAGAS integration should be a top priority.

Standard RAG — Pros & Cons

Strengths

  • Well-understood, battle-tested since 2020
  • No LLM required at ingestion time (just an embedder)
  • Fast updates — add a document, embed, done
  • Highly composable — swap any component independently
  • Works well for single-hop factual Q&A and summarisation
  • Rich ecosystem (LangChain, LlamaIndex, Haystack)
  • Evaluation tooling (RAGAS) is mature

Weaknesses

  • No multi-hop reasoning — "What connects A to B?" fails without explicit graph structure
  • Lost-in-the-middle — LLMs perform worst on evidence in the middle of a long context window
  • Chunk boundary fragmentation — semantic continuity broken by fixed chunk splits
  • Irrelevant retrieval poisoning — retrieved noise degrades generation even with correct chunks present
  • No entity awareness — disambiguation requires entity linking
  • Static retrieval — vanilla RAG retrieves once; iterative/recursive retrieval requires architectural extensions

Architecture Overview

Full Stack

Backend (port 8000)

  • FastAPI + Uvicorn
  • NetworkX MultiDiGraph + PageRank + Louvain communities
  • FAISS (CPU) + all-MiniLM-L6-v2 (384-dim)
  • Qwen 3.5B GGUF via llama.cpp (AMD Vulkan, port 8080)
  • HuggingFace Inference API as fallback
  • 993 passage chunks from Claude Mythos PDF
  • Alpaca prompt template

Frontend (port 3000)

  • Next.js 16 + React 19 + TypeScript
  • D3.js 7 interactive graph visualisation
  • Chart.js 4 analytics dashboard
  • WebSocket streaming (pipeline steps + tokens)
  • Self-reconnecting WebSocket manager
  • 10-minute query timeout for slow GPU

LLM 4-Tier Fallback

  1. Local llama.cpp — LOCAL_LLAMA_CPP_URL (AMD GPU via Vulkan, port 8080)
  2. HuggingFace Inference API — HF_TOKEN + HF_MODEL_ID
  3. Gradio client — HF Space fallback
  4. Simulation — deterministic mock (no LLM; last resort)

The 6-Step Query Pipeline

Defined in backend/pipeline/query_engine.py — the core intelligence of the system.

1
Intent Classification — LLM extracts entities and classifies query type: factual, multi-hop, aggregative, or comparative. Determines downstream traversal strategy.
2
Semantic Node Matching — Query is embedded with all-MiniLM-L6-v2 (384-dim), searched against the FAISS index to find the top-k graph nodes most similar to the query.
3
Graph Traversal — Multi-hop BFS + PageRank over the NetworkX MultiDiGraph, up to 6 hops from seed nodes. Discovers relationship chains not findable by flat vector search alone.
4
Passage Retrieval — Cosine search over the chunk_store (993 chunks). Keyword boosting: if 3+ query keywords match a chunk, that chunk overrides the cosine top-1. Collects chunks from top_page, top_page+1, top_page+2 (3-page span for boundary handling).
5
Context Fusion — Stitches graph traversal paths + passage chunks into a grounded prompt. Quote-continuation trim and _norm_quotes() for "Continue this section" query types.
6
LLM Generation — Sends to local Qwen 3.5B with Alpaca template. Falls back to direct passage extraction if output fails _answer_is_corrupted() check (Alpaca bleed-through, instruction-echo, empty output).

GraphRAG++ Strengths

What GraphRAG++ Does Well

  • Multi-hop reasoning — BFS + PageRank traversal up to 6 hops; standard RAG cannot do this
  • Hybrid retrieval — graph paths + passage chunks give structural + semantic context simultaneously
  • Community detection — Louvain communities enable global summary queries
  • Local-first — full pipeline runs on AMD GPU via Vulkan llama.cpp; no cloud required
  • Streaming UX — WebSocket broadcasts pipeline step events and token-level generation progress
  • Corruption detection — _answer_is_corrupted() catches Alpaca bleed-through and instruction-echo
  • Intent classification — adapts retrieval strategy per query type
  • Full ingestion pipeline — PDF, code, image, ZIP, directory walk all supported

Current Limitations

  • Outdated embedding model — all-MiniLM-L6-v2 (MTEB ~56) is ~15 points behind SoTA
  • No BM25 / sparse retrieval — exact-keyword queries rely on keyword-boost heuristic (3+ hits), not a real sparse index
  • No reranking — retrieved chunks are not cross-encoder reranked before context fusion
  • No evaluation framework — no RAGAS or equivalent; cannot measure if changes improve quality
  • No query expansion — no HyDE, RAG-Fusion, or query decomposition; single-pass retrieval only
  • Corpus bias — 993 chunks primarily from Claude Mythos PDF; answers to non-Claude-related queries will be weak
  • Triple extraction quality — LLM-extracted triples from ingested docs may be noisy; no validation step
  • No contextual embedding — chunks are embedded raw; Anthropic's contextual retrieval not applied
  • Static FAISS FlatIP — exact but won't scale past ~50K chunks

Key Technical Gaps

Gap 1 — Embedding quality: all-MiniLM-L6-v2 MTEB score of ~56 vs BGE-M3 at ~70. Every retrieval step is bottlenecked by this 14-point gap. Upgrading the embedding model improves steps 2 and 4 simultaneously.

Gap 2 — No evaluation: The system has no way to measure whether it's working well or badly. Queries that appear to return reasonable text may be hallucinating. RAGAS integration is blocking for any serious development iteration.

Gap 3 — Keyword boost heuristic: The "3+ keyword match" override in Step 4 is a brittle heuristic. Real BM25 sparse retrieval + RRF fusion would handle this more robustly while also improving exact-match queries.

Gap 4 — Single-pass retrieval: Queries are executed once with no expansion. HyDE or RAG-Fusion would significantly improve recall on ambiguous or multi-faceted questions.

Gap 5 — No contextual chunk embedding: Chunks are embedded raw. Anthropic's Contextual Retrieval (prepend 50–100 token LLM-generated context to each chunk) reduces retrieval failures by 35–67% and requires only a one-time re-embedding pass.

Integration Recommendations Section 4

How to make GraphRAG++ better by combining lessons from Graphify and Standard RAG best practices. Ordered by impact and implementation difficulty.

Immediate Wins (Low Effort, High Impact)

Priority: High · Effort: Low

1. Run Graphify on the GraphRAG++ Codebase Itself

Install Graphify (uv tool install graphifyy && graphify install) and run it on the GraphRAG++ Python backend. The PreToolUse hook will give Claude Code structured architectural awareness when helping with development. Token savings of 49–71x mean Claude can understand query_engine.py, graph_builder.py, and llm.py relationships without reading all files. This is developer-tooling only — no backend code change needed.

Priority: High · Effort: Low–Medium

2. Add RAGAS Evaluation

Before any other optimization, install ragas and create a golden test set of 20–50 (query, ground-truth-answer) pairs. Run RAGAS metrics (Faithfulness, Answer Relevancy, Context Precision, Context Recall) after every significant pipeline change. Without this, you cannot know if changes help or hurt. Use USE_SIMULATION=true mode for cheap evaluation runs during development.

Priority: High · Effort: Medium

3. Upgrade Embedding Model to BGE-M3

Replace all-MiniLM-L6-v2 (MTEB ~56, 384-dim) with BAAI/bge-m3 (MTEB ~70, 1024-dim). BGE-M3 provides dense + sparse + multi-vector retrieval in a single model — immediately enabling hybrid retrieval without adding BM25 as a separate component. Re-embed all 993 chunks. Update FAISS index to 1024-dim. The FAISS index stays FlatIP at this corpus size.

Priority: Medium · Effort: Low

4. Replace Keyword-Boost Heuristic with BM25

The current "3+ keyword match" override is brittle. Add rank_bm25 as a sparse retriever over the chunk store text. Merge BM25 scores with cosine scores using RRF (k=60). This is ~30 lines of code in chunk_store.py and eliminates the fragile keyword counting logic while improving exact-match retrieval quality.

Medium-Term Improvements

Priority: Medium · Effort: Medium

5. Apply Anthropic's Contextual Retrieval

For each of the 993 chunks, generate a 50–100 token context blurb using the LLM ("This chunk discusses X in the context of Y...") and prepend it before embedding. Re-embed all chunks with the context-enriched text. Anthropic reports 35% failure reduction from contextual embeddings alone, and 67% with contextual embeddings + BM25 + reranking. This is a one-time preprocessing pass — chunks are stored as enriched text; the query-time pipeline is unchanged.

Priority: Medium · Effort: Medium

6. Add Cross-Encoder Reranking (Step 4.5)

After cosine retrieval returns top-k chunks (Step 4), add a cross-encoder reranking step using cross-encoder/ms-marco-MiniLM-L-6-v2 or similar. Cross-encoders score (query, chunk) pairs with full attention — giving +33–40% accuracy over bi-encoder retrieval alone. Only rerank top-20 candidates. This slots cleanly between Step 4 (passage retrieval) and Step 5 (context fusion) in query_engine.py.

Priority: Medium · Effort: Medium

7. Implement Graphify-Style Code Graph Ingestion

When a user ingests a code directory via /ingest/directory, apply Tree-sitter AST parsing (like Graphify does) instead of treating code as plain text. Extract function definitions, class hierarchies, imports, and call graphs as typed edges in the NetworkX graph. This dramatically improves multi-hop queries like "what calls cosine_search and what does it return?" — questions that naive text chunking cannot answer structurally.

Priority: Medium · Effort: Medium

8. Add RAG-Fusion Query Expansion

Before the main retrieval pipeline (before Step 2), generate 3 query variants using the LLM (different phrasings of the same question), run retrieval for each variant in parallel, then merge all retrieved chunks via RRF. This improves recall on ambiguous queries by +10–15% with minimal latency overhead on local GPU. Enable selectively for multi-hop and comparative query types; skip for factual.

Long-Term Architecture Improvements

Priority: Strategic · Effort: High

9. Self-RAG Critique Loop

After LLM generation (Step 6), add a critique pass where the LLM evaluates its own output for faithfulness to the retrieved context. If faithfulness score is low, trigger a second retrieval pass with a refined query. This closes the loop between generation and retrieval — the system gets smarter per query rather than retrieving once and hoping. Requires Qwen 3.5B to handle critique prompts well; may need the HF-hosted model for reliable critique.

Priority: Strategic · Effort: High

10. Graphify MCP Server Integration

Run Graphify in MCP server mode alongside the FastAPI backend. Expose Graphify's query_graph, get_neighbors, and get_summary tools to the query pipeline so that code-structure queries can be answered by the AST-based graph (Graphify's strength) while document/knowledge queries use the existing NetworkX entity graph. This creates a dual-graph architecture: one for code structure, one for knowledge relationships.

Priority: Strategic · Effort: High

11. Upgrade to HNSW + Parent-Child Chunking

As the chunk store grows past 50K chunks, switch FAISS from IndexFlatIP to IndexHNSWFlat for sub-millisecond search. Simultaneously adopt parent-child chunking: index small (128-token) child chunks for precision retrieval, but return the larger (512-token) parent chunk as context. This decouples retrieval granularity from context richness.

Priority: Strategic · Effort: Medium

12. RAPTOR Hierarchical Graph Overlay

After initial triple extraction builds the node-level graph, run RAPTOR-style clustering: embed all entity nodes, cluster via UMAP + Gaussian Mixture, summarise each cluster using the LLM, add summary nodes to the graph as "community summaries." This enables the graph to answer aggregative queries ("summarise all entities related to safety") by retrieving from the summary layer rather than enumerating all individual nodes — which is what Louvain communities partially provide but without the LLM-generated summary text.
